# 产品边界

[English](../COMPARISON.md) · 中文

BigRobot 是接管已有聊天账号的平台，不是通用工作流搭建器、聊天前端或插件市场。

## 是什么

一个进程连接模型 API 和协议端，把权限、审批、审计、记忆和检索放在引擎里，而不是塞进提示词。账号是中心：群、成员、文件和历史都是一等对象，动作受策略约束。

## 不是什么

| 不是 | 因为 |
|---|---|
| 可视化工作流平台 | 目标是在群里长期活着，不是拖一条流水线 |
| 自托管 AI 聊天前端 | 目标是替人办事的助手，不是另一个聊天框 |
| 工单系统 | 坐席接管只是一个模块，不是产品骨架 |
| 只会回话的 IM 框架 | 回话只是起点；执行需要审批和可追溯 |

## 差异落在哪

| 方面 | BigRobot |
|---|---|
| 账号模型 | 接管现成账号，并把它真实的内容摊开 |
| 权限 | 风险分级 + 主体分级；破坏性动作强制审批 |
| 审计 | 哈希链记录，可在控制台校验 |
| 没有模型 Key | 规则和检索照常运行，群不会静默 |
| 角色 | 结构化角色卡、漂移检查、提醒和长期记忆 |
| 多账号 | 会话、记忆、动作按机器人账号隔离 |
| 扩展 | 声明式 HTTP 扩展与 MCP；核心进程不跑 Python 插件 |

## 主动保留的短板

- **平台数量少**：QQ 是深路径，新增平台应该是一份声明，而不是第二个产品。
- **没有插件市场**：远程 Python 插件跑在核心进程里，与权限模型冲突。
- **没有可视化编排**：配置就是编排面。
- **不比赛功能数量**：护城河是让账号长期活着所需的脏活——记忆、提醒、权限、审批、审计、人设一致性、互刷护栏和无模型降级。

比较的重点不是“谁的功能格子里打勾多”，而是“新增一个能力、一个平台或一个账号时，成本有多低，控制会不会丢”。BigRobot 围绕这个成本设计，同时保住账号和边界。
