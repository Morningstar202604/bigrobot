# 与同类项目的差异

> 这份文档只回答一件事：**我们和谁不一样，凭什么是这样**。
> 不复述每家的产品介绍，也不抄它们的 README。要细节去看对方文档。

## 一、我们是什么，不是什么

**BigRobot 是「接管账号的机器人平台」**：一个进程，接多家模型 API + 多个协议端，
把权限、审批、审计、记忆、检索做在引擎里，而不是做在提示词里。

它**不是**：

| 不是 | 因为 |
|---|---|
| 可视化工作流平台（Dify / n8n / Flowise） | 我们要的是"在群里长期活着"，不是拖拽一条流水线 |
| 自托管 AI 前端（Open WebUI / LibreChat / LobeHub） | 它们解决"给人一个聊天框"，我们解决"机器人替人办事" |
| 客服工单系统（Chatwoot） | 坐席接管只是我们的一个模块，不是产品骨架 |
| 只会聊天的 IM 框架（AstrBot / LangBot / Koishi） | 我们不满足于"接上就能回话"，还要能执行、能审批、能追溯 |

## 三、和 AstrBot 差在哪（最直接的竞品）

两者都能接 QQ、都能调模型、都有插件概念。差别不在功能表，在**新增一个能力的单位成本**：

| 维度 | BigRobot | AstrBot |
|---|---|---|
| 加一个工具 | 改 `core/tools.py` 三处（实现 + `TOOL_META` + `_builtin_impls`） | 放一个插件目录，热加载 |
| 加一个平台 | 改 `gateway/`，适配器目前只有 OneBot v11 一路 | 装适配器插件，18+ 平台 |
| 破坏性动作 | 内建 L0/L1/L2 × T0–T3 + 审批单 + 哈希链，默认强制人工批 | 无内建分级，靠插件自觉 |
| 无模型 Key | 规则 + 检索链路照常，群聊不静默 | 基本不可用 |
| 长期记忆/提醒/人设 | 内建结构化角色卡、漂移守卫、自然时间提醒 | 人格 = prompt + 工具 + KB 逐项绑定 |
| 许可 | MIT | AGPL-3.0-or-later + 附加 EULA |

**结论（不含糊）：**

- **单点深度**我们已经更强，且短期内它不会追——审批链、审计链、降级链是架构决定，不是插件能补的。
- **广度与边际成本**我们明显更弱。它加一个平台是一个插件；我们是一段适配代码。
- 所以"谁更强"取决于问法：**问"在 QQ 群里长期不出事"，我们强；问"三个月接 10 个平台"，它强。**

这条差距不是靠"多写几个适配器"解决的，而是靠**把能力出口标准化**：

1. `gateway/adapters/` 的 `PluginManifest` / `PluginRegistry` 目前只活在测试里，网关启动流程没接→ 这是已知断缝，必须先接上，否则"插件化"只是文档。
2. 对外暴露 OpenAI 兼容 `/v1/chat/completions`，让任何前端/编排平台把 BigRobot 当模型用。
3. MCP server（已有）/ MCP client（缺）——client 是补广度最省力的一条路：接一个 MCP server 就多一批工具，不用改 `core/tools.py`。

## 四、声称 vs 落地（实测核查）

数字全部来自 2.0.0 这一轮的真实运行，不引用旧 README。

| 声称 | 核查方式 | 结论 |
|---|---|---|
| 55 个内置工具 | `GET /api/agent/health` → `tool_count` | ✅ 55（旧文档写 42，已更正） |
| 原生 function calling + JSON 降级 | `core/llm.py:_post_chat` 四级降级链 | ✅ 有回归测试 |
| ReAct 多步 + 五维预算 | `core/agent_loop.py` + 26 例测试 | ✅ |
| FTS5 + 向量 + RRF | `core/retrieval.py` 索引重建/降级链 | ✅ 向量为可选依赖 |
| L0/L1/L2 × T0–T3 + 审批 | `core/actions/authz.py` / `registry.py` | ⚠️ 真实但**有缺陷**：审批分支跑在主体判定之前，陌生群成员也能生成审批单（待修） |
| 哈希链审计可校验 | `/api/admin/audit/verify` | ✅ e2e 覆盖 |
| 114 条 REST 路由 + 2 个 WebSocket | 路由装饰器计数 | ✅ |
| 28 张表 | `core/store.py` schema | ✅ |
| 中英双语 | `scripts/i18n_gap.py` | ✅ 源码 msgid 438 / en.ts 键 751 / 缺失 0 |
| 免 Key 可跑 | 无 Key 实例实测 | ✅ `现在几点` → `rule_react`，提醒真建 |
| 测试规模 | `pytest tests -q` | ✅ 976 passed / 3 skipped（2 个失败是环境依赖） |

**已修掉的旧问题**（不再作为"已知缺陷"挂在文档里）：`.env` 从未被加载、免 Key 时 QQ 静默、
无 Prometheus 直方图、搜索不可用、正文抽取差。

**仍然诚实承认的**：

- 插件缝没接进网关启动流程（见上）。
- `core/main.py` 是 1917 行的单函数 `create_app`，95 条路由挤在里面——这是**改造成本**，不是功能问题。
- 7 条 `async def` 路由里同步跑 SQLite/文档解析，实测导入 291 段 docx 时全站 `/healthz` 峰值 2.2s（待改线程池）。

## 五、明确不做

- 不做插件市场 / 远程安装：与"接管账号、权限内建"的模型冲突。
- 不做可视化编排：编排在配置里，不在画布里。
- 不堆 IM 适配器数量：先让 QQ 这条链路能长期活着。

## 六、一句话

我们的护城河不是"功能多"，是**在一个群里长期活着所需的全部脏活**：
记忆、提醒、权限、审批、审计、人格、防互刷、无模型降级。
这些在大平台上是企业版功能，在这里是默认行为。
